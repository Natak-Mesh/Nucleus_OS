# CLI Terminal Menu — Planning

Power user / field tech tool for troubleshooting, configuration, and deeper system metrics. Provides capabilities beyond the web UI: interactive TUIs, full CLI access to mesh/radio/Reticulum tools, network diagnostics, and shell access.

## Web UI vs CLI Tool

The **web UI** is for quick status checks and config changes from a phone or browser — it deliberately simplifies things.

The **CLI tool** is the power interface. Things you can't do (or shouldn't try) in a browser:

- **Interactive TUI tools** — ncdu, btop, journalctl -f, NomadNet. Need a real terminal.
- **Network diagnostics** — iperf3 (bandwidth test between nodes), tcpdump (packet capture), mtr (path analysis). Inherently interactive or produce streaming output.
- **Full Meshtastic CLI** — web UI wraps a subset. CLI gives `--export-config`, `--traceroute`, `--sendtext` with arbitrary options.
- **Reticulum advanced ops** — rnx (remote execute on another node), rncp (file transfer), rnprobe. Interactive or need user input.
- **Shell access** — sometimes you just need bash.
- **Zero-config connection** — auto-discover and connect without knowing IPs.

## Architecture

Two pieces:

**Pi-side (this repo):** `nucleus-menu.sh` presents a numbered menu of curated CLI tools. `nucleus-status.sh` shows a one-page system summary. Both live in `/opt/nucleus/bin/`.

**Laptop-side (separate repo):** `nucleus-tools` — a pip-installable Python package (`pip install nucleus-tools`). User types `nucleus` → tool auto-discovers the node, SSHes in, launches the menu. Repo: `Natak-Mesh/nucleus-tools`.

No sshd_config changes needed. The client does `ssh -t natak@host /opt/nucleus/bin/nucleus-menu.sh`.

## Build Order

1. Pi-side first — menu + status script, testable via plain SSH
2. Laptop client second — polished wrapper around what already works

## Node Discovery

### Connection Scenarios

The laptop can reach a Nucleus node three ways, and eth0 mode affects what works:

| Scenario | Pi's eth0 IP | Gateway detection | mDNS |
|----------|-------------|-------------------|------|
| **Direct cable, LAN mode** | `10.20.X.1` (predictable, Pi runs DHCP) | ✅ Gateway = Pi | ✅ |
| **Same router/network, WAN mode** | DHCP-assigned (unpredictable) | ❌ Gateway = router, not Pi | ✅ |
| **Laptop on Pi's WiFi AP** | N/A (br-lan `10.20.X.1`) | ✅ Gateway = Pi | ✅ |

Gateway detection only works when the Pi IS the gateway. In WAN mode on a shared network, the Pi is just another device — gateway detection finds the router, not the Pi.

### Discovery Strategy

**mDNS is the primary discovery method.** Avahi is already running on every Pi (hostname `XXXX-nucleus`). It works in all three scenarios as long as laptop and Pi share an L2 segment.

We add an avahi service file so each Pi advertises `_nucleus._tcp` — this lets us browse for the service specifically and include metadata (serial, mesh IP, version) in TXT records.

**Discovery order:**
1. **mDNS service browse** for `_nucleus._tcp` — finds all Nucleus nodes on the local L2 segment
2. **Gateway check** as supplement — if gateway matches `10.10.X.1` or `10.20.X.1`, it's a direct-attached Nucleus
3. **Mesh enumeration** — SSH into the found node, query Babel routing table for other mesh nodes (10.20.1.X)
4. **Manual fallback** — `nucleus --host 192.168.1.50` when auto-discovery can't work (mDNS blocked, VPN, etc.)

### Multi-Node Selection

A laptop connects to one node directly, but through that node can reach every node on the mesh via routing.

```
$ nucleus
🔍 Scanning...

  1  0009-nucleus  10.20.9.1    direct (eth0 cable)
  2  0022-nucleus  10.0.0.245   same network (mDNS)
  3  0008-nucleus  10.20.1.8    mesh (via 0009)
  4  0012-nucleus  10.20.1.12   mesh (via 0009)

  Select [1]:
```

### Pi-Side: Avahi Service File

Generated by `config_generation.sh` from mesh.conf values → `/etc/avahi/services/nucleus.service`:

```xml
<service-group>
  <name>Nucleus XXXX</name>
  <service>
    <type>_nucleus._tcp</type>
    <port>22</port>
    <txt-record>serial=XXXX</txt-record>
    <txt-record>mesh_ip=10.20.1.X</txt-record>
  </service>
</service-group>
```

## Evaluated and Dropped

### netwatch (https://github.com/matthart1983/netwatch)

Rust-based TUI network monitor with nice tx/rx rate graphs, connection tracking, and a flight recorder feature. **Dropped** because it reads kernel `operstate` to determine interface status and misreports both:

- **wlan1 (802.11s mesh):** Kernel reports `state DORMANT` / `NO-CARRIER` even with active mesh peers — this is a Linux kernel quirk where carrier detection doesn't apply to mesh mode interfaces. netwatch shows it as "down."
- **tailscale0 (TUN/TAP):** Kernel reports `state UNKNOWN` which is normal for tunnel devices. netwatch shows it as "down."

Since these are the two most critical interfaces on a Nucleus node, the misleading status makes the tool more confusing than helpful. Fixing it would require forking the Rust source — out of scope.

### Redundancy notes

- **htop** replaced by **nucleus-status** for system overview (htop shows too much noise — all tailscale threads etc.)
- **ss** replaced by **portrm** (same data, prettier output)
- **free/df** covered by **nucleus-status** one-page summary
- **top** superseded by htop/btop

## nucleus-tools Client Package

Repo: `Natak-Mesh/nucleus-tools`

User experience:
1. `pip install nucleus-tools`
2. Plug Nucleus into laptop (eth0) or connect to AP WiFi
3. Type `nucleus`
4. Auto-discovers node(s), pick from list if multiple found, connects, menu appears

Features:
- mDNS service browse (`_nucleus._tcp`) — primary discovery, works in all connection scenarios
- Gateway detection as supplement — catches direct cable (LAN mode) and AP WiFi
- Mesh peer enumeration — SSH into found node, query Babel for all mesh nodes
- Manual fallback (`nucleus --host <ip>`) — for when mDNS is blocked
- Remember last connection — `nucleus` reconnects, `nucleus --scan` forces re-discovery
- Multi-node selection — list all reachable nodes, pick one
- Cross-platform (macOS, Linux, Windows)
